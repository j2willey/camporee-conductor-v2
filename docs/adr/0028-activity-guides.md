# ADR-0028 — Activity guides: v1's Game Guides, generated from the design

Date: 2026-11-11 · Status: Accepted (issue #44; breakdown OK'd by Jim, 2026-11-11)

## Context

v1 printed a **Game Guide** for each game from a Handlebars template (`public/templates/gameguide.md`, rendered with
`marked`). Game Leaders get them on the morning of the event. #44 brings them to v2 at v1 parity, read-only from an
imported Event. They are separate from the event-wide Program Guide (ADR-0018, #5).

## Decision

1. **Code says _Activity guide_** (CLAUDE.md rule 1). On screen, the label comes from the Competition: "Patrol Games
   guides", as v1 titled them (`${league.label} Guides`). No new terminology field.
2. **Pure generation in `packages/program-guide`,** beside the Program Guide: `buildActivityGuide` (a model) and
   `renderActivityGuidesHtml` (one standalone, print-ready HTML page with no scripts and no external files). It
   shares `escapeHtml` and the print approach. The Composer API serves the page behind the Org sign-in, as it does
   the Program Guide (#38).
3. **Three parts, each starting a new page,** as in v1, written for different people:
   - **The script** (competitors; "Read this to the \<Team or Group label\> on arrival", by the Competition's
     level): Background (`story`), The Objective (`objective`, v1's `challenge`), Instructions (`description`),
     Rules & Constraints (`rules`).
   - **The Judge's playbook:** Scoring Overview (`timeAndScoring`), Notes & Background (`notes`, when given), then
     the **custom sections** in order (Jim, 2026-11-11). The v1 import puts `scoring_notes` ("Scoring Notes") and
     `references` ("References") there, and v1 printed both in the playbook. Last comes Station Reset (`reset`, or
     "No specific reset required").
     - A competitor-facing custom section (v1's `instructions`) would print in the playbook too. Matching on
       titles to move it would be guesswork; none of Circus 2026's custom sections are of this kind.
   - **Logistics and setup:** Supplies (`supplies`, under their `group` headings, with quantities, or "No
     supplies listed."), Staffing, and Setup Instructions.
4. **The header** is the Activity's title, with its number in front once guides are printed together (#44 PR 2).
   Under it: the Competition's label and the tags. v1's ID / Category / Type line is dropped: category and type
   were v1's league and kind, which v2 holds as the Competition and `scoringType`. The footer reads "Generated by
   Camporee Conductor".
5. **Activity text is Markdown,** as in v1 (Circus 2026: lists in 13 Activities, bold in 2). It is rendered by a
   **small subset renderer that escapes first**: paragraphs, line breaks, bulleted and numbered lists (one nested
   level), bold and italic. Raw HTML stays text, and there are no images or links yet. The text is written by Org
   members and served on the Composer's domain, so a full Markdown library would need a sanitizer. The subset is
   exactly what Circus 2026 uses. Images come by asset id later (ADR-0012, #7).
6. **Parity test:** no printed 2026 guides survive. So for every Circus 2026 Activity, every non-empty v1 `content`
   value in `fixtures/circus-2026/v1-source/games/` must appear in the same part of the v2 guide. Supplies are
   checked against the imported `supplies` (the import's own tests cover the text → items step).

## Printing several guides (2026-11-11, #44 PR 2)

7. **Numbers:** each Activity's number is the first letter of its Competition's label plus its position in that
   Competition, in Event order: `P1`… for Patrol Games, `T1`… for Troop Challenges, `E1`… for Exhibitions, as v1
   printed them. If two Competitions' labels start with the same letter, both use the Competition's position
   instead (`1-3`, `2-3`). The number is part of the Activity's guide wherever it prints, and is worked out in
   the package (`activityGuideNumbers`).
8. **A Guides page in the Composer:** Activities by Competition, with All / None, all ticked at first, and a
   **Two-sided** box (on by default). It opens one print page with the picked guides in Event order.
9. **Two-sided: each guide starts on a right-hand page** (Jim, 2026-11-11), so a packet folds per Activity. Chrome
   ignores CSS `break-before: right`; a rendered PDF in 2026-11 put no blank pages in. So the page carries **one
   small inline script**, the only exception to "no scripts". It measures each part at the printed width,
   works out how many pages each guide takes, and adds a blank page after any guide that ends on a right-hand
   page, as v1 did. The page arithmetic is a pure function in the package, unit tested, and the page embeds that
   same function's source, so what's tested is what runs. Single-sided printing adds no blank pages and runs no script.

## The supplies list (2026-11-11, #44 PR 3)

10. **v1's `printSupplies`, from the Guides page,** for the same picked Activities:
    - **Content:** each Activity in Event order, headed by its number and title. Its supplies are listed under their
      `group` headings as sub-items, each written "item (quantity)" when a quantity is given. An Activity with none
      reads "No supplies listed."
    - **Two modes, as in v1:** **one Activity per page**, or **continuous**. In continuous mode an Activity longer
      than 30 lines is split, and each later piece is headed "\<number\> \<title\> (cont.)", v1's fixed split.
      Browsers don't say where a printed page breaks.
    - **Per Activity, not totals:** quantities are free text ("4–5", "1 per judge"), so they can't be added up.
    - **Generation:** pure, in `packages/program-guide` (`buildSuppliesList`, `renderSuppliesListHtml`). One
      standalone page with no scripts.

## Consequences

- Printing guides from the Collator box on the day is later, not parity (Jim, 2026-11-11).
- The Program Guide's teasers can reuse the Markdown subset.
